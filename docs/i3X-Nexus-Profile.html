i3X Nexus Profile

A profile of CESMII i3X 1.0Status: draft for comment

1Abstract

This profile defines an i3X nexus: one i3X 1.0 endpoint per site that serves live values, history, business records and media (video, images, audio) in a single address space. Writes are governed: each one is authorised, recorded, reversible and checked afterwards. The nexus is redundant, so it keeps working through the loss of a node or of the site's uplink.

OPC UA, i3X and MCP already define how data moves and how models reach tools. No existing standard defines who may write, under what authority, with what record of why, how a write is undone, or how anyone checks afterwards that it did what it claimed. Software agents now act on plant data, and that makes the gap urgent. This profile fills it while staying inside the i3X 1.0 contract. A client that knows nothing about the profile keeps working.

The profile is product-neutral. It is meant to let an operations or decision platform that holds authority limits, a historian, an MES or CMMS, a camera system and AI agents interoperate through one contract. Any system can implement it, as a server or as a client.

Core mechanism. A nexus never writes to a plant system directly on a client's behalf. Every governed write is a WriteRequest object. It carries its actor, its authority and its justification, and moves through requested → approved → applied → verified, or ends rejected, expired or rolled_back. Clients read it and subscribe to it over plain i3X 1.0.

3Scope

In scope

  • One address space per site covering four data classes: realtime, historical, transactional and media.
  • Governed writes, at three tiers.
  • Provenance, rollback and outcome verification for every governed write.
  • Priority, load shedding and scaling behaviour.
  • Redundancy targets and failure behaviour.
  • A security posture aligned to IEC 62443.
  • Conformance levels.

Out of scope

  • Control. A nexus MUST NOT run a control loop, hold an interlock or form part of a safety function. Setpoint writes, where allowed, pass through the site's existing control layer.
  • Replacing historians, MES, CMMS or ERP. A nexus serves them through adapters and holds only data it owns or data with no other home.
  • New protocols. i3X is the northbound contract. OPC UA and MQTT are the expected southbound sources. Device protocols such as Modbus or EtherNet/IP are reached through an existing gateway.
  • Model inference. Agents may propose writes. The path that decides, applies and verifies a write is deterministic and contains no model call.

5Data classes

All four classes are served as ordinary i3X objects in one hierarchy. They differ in where the truth lives and in how each i3X operation is answered.

  • NX-1A nexus MUST keep the source timestamp of a value unchanged. It SHOULD expose its own receive time in metadata.
  • NX-2Quality MUST follow the OPC UA Good / Uncertain / Bad classes. A realtime value bound to a source with a declared update period, and not refreshed within three times that period, MUST read Uncertain, with its last value kept. Report-by-exception sources (OPC UA subscriptions, Sparkplug, most MQTT publishers) are silent when steady, so they declare no period and staleness does not apply to them. A value whose source is lost MUST read Bad, and SHOULD be served without a value, so it cannot be mistaken for a reading.
  • NX-3A nexus MUST NOT substitute any value for one it cannot obtain: no default, no demo data, no interpolation. A failed source shows only as degraded quality or a per-item error.
  • NX-4A failed history store MUST return an error for the request. It MUST NOT return an empty series, which a client would read as "no data".
  • NX-5Every change to a transactional record MUST create a new version with its writer, time and an idempotency key. Versions MUST NOT be updated or deleted. The record's history is its version list.
  • NX-6A record held by an external system of record MUST be served as a projection carrying that system's version, and MUST NOT be changed through the nexus except as a W1 write (§7).

6Media: video, images and audio

i3X values are JSON and its subscriptions are text streams. Media therefore follows one rule: references travel in i3X, and bytes travel out of band.

Object typeIn i3XBytes
MediaItemAn image, clip or audio sample. Its value carries sha256, mimeType, size, status, capturedAt, optional durationMs/width/height, and href, a short-lived signed URL. Related by CapturedBy to its device and by Documents to the alarm, reading or record it documents.Media store, through href
MediaStreamA live camera or microphone feed. Its value carries codec, resolution and a viewer URL. Stream health (online, frame rate, dropped frames) is ordinary realtime values with quality.Media gateway (WebRTC, HLS). Never through the i3X API
MediaIntakeThe writable element through which new media is announced.None
  • NX-10A MediaItem's element id MUST be derived from its content hash: {nx-prefix}:media:<sha256>. A repeated request therefore names the same item, and a citation proves which bytes it cites.
  • NX-11Upload: a client writes { sha256, mimeType, size, … } to the MediaIntake with PUT /objects/value. The item appears with status awaiting_bytes and an upload href. Bytes sent to that URL MUST be hashed on arrival. A mismatch, or more bytes than declared, MUST be discarded, and the item stays awaiting_bytes. On a match the item becomes available.
  • NX-12Signed URLs MUST expire, by default after at most 10 minutes. They SHOULD be stable within a short window, so that reading an item twice does not register as a change to subscribers.
  • NX-13Accepted media types MUST be an explicit allow-list. Executable and archive types MUST be refused.
  • NX-14Media cited by a WriteRequest, ledger entry or outcome observation MUST be retained as long as the ledger is.
  • NX-15Live streams and media byte transfer MUST run outside the capacity that serves i3X values, with a bandwidth cap per conduit (§8).
  • NX-16A media gateway MUST pull devices; nothing may publish into it. Every viewer MUST be authorised by the nexus, by a short-lived signed token carried in the stream's viewer URL and valid for that stream only.
  • NX-17Where a clip is cut around an event, it MUST be stored as a MediaItem that Documents the event and was CapturedBy the stream, and its window MUST be limited to what was actually recorded.

7Write governance

7.1 Tiers

TierMeaningExampleGate
W0 publishWriting into a namespace the principal ownsA decision record, an outcome observation, an outbound signalNamespace ownership
W1 recordCreating or changing a record in a system of recordOpen a work order, place a quality holdAuthority limit; approval above the delegated limit or on a boundary trigger
W2 setpointChanging a value the process acts onA temperature setpoint, a line speedDeclared write envelope, approval by a named person every time, read-back verification
  • NX-20Ownership for W0 MUST be tested against the namespace the server holds for the target's type, by exact match. A prefix match is not allowed, and the test MUST fail closed when the namespace is absent.
  • NX-21Agents MAY hold W0 rights in their own namespaces. For W1 and W2 an agent MAY only request. An agent MUST NOT approve a write.
  • NX-22A direct write to a governed target, for example PUT /objects/value on a setpoint, MUST be refused per item with status 403 and a message naming the intake element to use.

7.2 The WriteRequest object

Every W1 and W2 write is a WriteRequest object in {nx}. Its schema is in Annex A. It carries the target, the proposed value, the prior value and version, the actor and the role it acts for, a justification (a reference to a decision record and its falsification condition), the governing authority limit, reversibility, the compensation, an idempotency key, status, approvals, the application result and the verification result.

  • NX-23The governor MUST compute status and escalation itself and MUST ignore any values the writer supplies for them.

7.3 Lifecycle within i3X 1.0

i3X 1.0 has no create verb. A nexus therefore exposes one writable intake element per tier. A PUT /objects/value to the intake is an ordinary i3X write, and the governor turns it into a new WriteRequest.

sequenceDiagram
  participant R as Requester (person or agent)
  participant N as Write governor
  participant A as Approver
  participant S as System of record / gateway
  participant V as Verifier
  R->>N: PUT intake (request + idempotency key)
  N->>N: authenticate · ownership · tier · authority limit · envelope
  N-->>R: success; WriteRequest id (status requested)
  N->>A: approval needed (subscription event)
  A->>N: PUT WriteRequest.approvals (within own limit)
  N->>N: re-read target; compare to prior (stale → rejected)
  N->>S: apply
  S-->>N: acknowledgement
  N->>S: read back
  N->>N: applied → verified, or mismatch → compensate
  V->>N: after deadline: outcome observation (W0)
  • NX-24The WriteRequest id MUST be derived from the requesting principal and the idempotency key, so a retried PUT finds the existing request and creates no second one. Recommended derivation: {nx-prefix}:wr: followed by the first 24 hex characters of SHA-256(principal id, newline, idempotency key).
  • NX-26Because an i3X 1.0 write result carries no payload, a nexus SHOULD return the element ids it created or wrote, in request order, in a response header X-Nexus-Written (a JSON array, null for a failed item). A client that ignores it loses nothing.
  • NX-25The same intake pattern SHOULD be used to create any new record over i3X 1.0.

7.4 Checks before applying

  1. Identity. The principal is authenticated. Any role it acts for is one it is delegated to hold.
  2. Ownership (W0), as NX-20.
  3. Authority (W1/W2). The authority limit for the site and exception type is found. With no limit, the request reads no_decision_right and cannot be approved.
  4. Envelope (W2). The proposed value lies inside the target's declared range, rate of change and allowed states. A value outside is rejected, never clamped.
  5. Freshness. At apply time the target still holds the recorded prior value. If it does not, the request is rejected as stale. The apply itself SHOULD be conditional on the recorded version (for example HTTP If-Match), so a change that lands between the check and the write is also refused.
  6. Approval. W1 needs one approval at or below the delegated limit, and approval by the limit's owner role above it or on any boundary trigger. W2 always needs a named person. Requester and approver MUST be different principals.
  • NX-27A refusal by the system of record (a 4xx, or a conditional write refused as stale) rejects the request. A failure of the system of record (a 5xx, a timeout, no answer) MUST NOT: the approval stands, the request stays approved, and the governor retries. A governor that takes over MUST finish requests left approved or applied by its predecessor, re-reading the system of record first so that an apply that already happened is recorded, not repeated.

Escalation rule: escalates if exposure ≥ materiality threshold or any boundary trigger is present; no_decision_right if no limit exists; exposure_unknown if a limit exists but no exposure is stated; otherwise stays_local. The delegated limit decides who approves. It is not the escalation test.

7.5 Provenance

  • NX-30Every WriteRequest state change MUST append one ledger entry: request id, transition, principal, time, prior and new state, and the hash of the previous entry.
  • NX-31Ledger entries MUST NOT be updated or deleted. Verifying the chain MUST detect an edited, removed or reordered entry.
  • NX-32The ledger MUST be readable as the WriteRequest's i3X history, so an auditor needs no other interface.

7.6 Rollback

  • NX-33Rollback MUST be a new, linked WriteRequest (relationship Compensates) that applies the recorded compensation under the same checks. Erasing the original is not rollback.
  • NX-34If read-back does not match within the verification window, the governor MUST apply the compensation without further approval, because the approved state never existed. It MAY do the same on an envelope breach after apply, where the envelope permits auto-revert.
  • NX-35A request marked reversible: false MUST state that no compensation exists, and MUST be approved one level above the limit's owner role.

7.7 Verification

  • NX-36Immediate. After applying, the governor MUST read the target back and record the result. That proves the write landed and nothing more.
  • NX-37Outcome. When the justifying decision carries a structured falsification condition, a verifier evaluates it after its deadline against the system of record. It publishes the result as an outcome observation (a W0 write) related to the WriteRequest. The nexus stores the condition and the observation. It does not judge whether the decision was right.

8Load handling, scaling and priority

8.1 Priority classes

ClassContentsUnder load
P0 criticalAlarm and quality-change events; approvals; rollbacks; WriteRequest status changes; W2 read-back; failover traffic; GET /infonever shed reserved capacity
P1 operationsRealtime reads, subscriptions, streamsconflated latest value kept
P2 businessTransactional reads; W0/W1 requestsqueued then 429
P3 bulkHistory ranges, backfill, analytics, media bytes, enterprise replayshed first 503
  • NX-40The server MUST assign the class from the object type and operation. A caller MUST NOT be able to raise its own class. A caller MAY ask for a lower one.
  • NX-41Each class MUST have its own queue and concurrency budget, so no class waits behind another's work. P0 MUST have reserved capacity that other classes cannot borrow (default 20%), and MUST NOT be shed for load.
  • NX-42Under rising load, the nexus MUST shed P3 first, then P2, then conflate P1. Every refused request MUST receive 429 or 503 with Retry-After. Nothing is dropped silently, and no write is left half-applied.
  • NX-43In a subscription stream, P0 events MUST bypass conflation, MUST NOT be dropped, and MUST be written before other updates in the same flush. A client that falls past its P0 queue cap MUST be disconnected so it resynchronises, rather than missing events.
  • NX-44Southbound, P0 items SHOULD use their own OPC UA subscription with a short publishing interval, and MQTT QoS 1 or higher. On conduits the site controls, P0 traffic SHOULD be marked DSCP EF.
  • NX-45After an uplink outage, store-and-forward MUST replay P0 first, then P2, then the latest P1 values, then P3.
  • NX-46Per-principal rate limits MUST apply. History queries MUST be bounded by range and point count.

8.2 Adding capacity versus adding a nexus

A nexus is a unit of authority. One governor and one ledger serialise every governed write in its scope.

PressureResponseAutomatic
More readers or subscribersAdd read replicas that follow the event log and serve reads and streamsMAY
Heavy history queriesAdd history workers; push aggregation to the historianMAY
Source change rate beyond one nodeSpread drivers across nodes; one cache and logoperator
A site too large for one nexusShard by ISA-95 area. Each shard is a full nexus that owns its area and its authority limitsMUST NOT
A new site, or an area that must survive the rest failingA new nexus, federated into the enterprise tierMUST NOT
  • NX-47Creating a nexus or a shard changes an authority boundary. It MUST be a reviewed configuration change and MUST NOT happen automatically.
  • NX-48A nexus MAY mount another's namespaces as an upstream, keeping element ids. A write to a mounted element MUST be forwarded to the nexus that owns it, with the caller's own credential, and only that nexus's governor decides it.
  • NX-49A write forwarded between nodes or tiers MUST carry an idempotency key; the forwarding node mints one if the client sent none. A node that dies mid-request leaves an unknown outcome, and the key is what makes re-sending it safe.

9Availability and redundancy

  • NX-50A site nexus MUST keep reading, serving and governing writes for its site with the uplink down. An enterprise nexus MUST NOT be in the path of any site write.
  • NX-51A redundant site nexus MUST have two full nodes and a quorum witness. The witness holds only consensus state. The pair is active/active for reads and subscriptions, and active/standby for the governor. This is OPC UA's non-transparent redundancy applied to i3X.
  • NX-52A node that loses quorum MUST fence itself to read-only.
  • NX-53With the standby down, the nexus MUST report degraded redundancy in /info and MUST suspend W2.
  • NX-55The shared store under a redundant nexus MUST itself be redundant with automatic failover decided by a quorum of at least three members on separate hosts, and SHOULD replicate synchronously so an acknowledged record is never lost (RPO 0). Only a synchronous standby may be promoted.
  • NX-56Where the store's members run on different operating systems or C libraries, text indexes MUST use an OS-independent collation (byte-wise C), because a library change in sort order silently corrupts a replicated index.
  • NX-54Subscription state MUST survive failover. A client reconnecting to the other node MUST be able to resume from its last sequence number.

10Security

The read path targets IEC 62443-3-3 security level SL 2 and the write governor targets SL 3. Development follows 62443-4-1 and components follow 62443-4-2.

Zones and conduits

  • NX-60A site nexus MUST be its own zone in the site DMZ. Southbound conduits MUST be opened by the nexus, outbound, to the gateway and broker.
  • NX-61The only path from the nexus into the plant network that writes MUST be the W2 conduit to the gateway: one port, one certificate, disabled unless W2 is enabled.
  • NX-62The uplink to an enterprise tier MUST be opened outbound from the site. A site nexus MUST NOT accept connections from the internet.
